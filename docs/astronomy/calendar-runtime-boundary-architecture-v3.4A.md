# Runtime boundary architecture for Phase 3B.4.4B (decision gate, v3.4A)

**Status: RECOMMENDATION. Not applied; ratification required in 3B.4.4B.** Nothing in production changed.

## 1. The contradiction, stated plainly

- The authority spec defines the domain boundary as **T_JPL = ceil(R_JPL)**, an exact integer TT millisecond, and golden-v4 tests T − 1 ms / T / T + 1 ms at T_JPL.
- The approved runtime engine (ERFA) is **accurate** to ≤ 0.5 s against JPL (max 0.376 s). It is **not identical**: its own canonical T equals T_JPL in **16 of 4,824** crossings and differs in 4,808, by up to 377 ms (median 74 ms). ERFA is later in 1,505 crossings and earlier in 3,303.
- "ERFA is accurate to ≤ 0.5 s" and "ERFA produces the JPL millisecond boundary" are different statements. Only the first is true.
- Measured consequence: an audit evaluator using ERFA boundaries fails **115 of 611** golden-v4 Group B fixtures, all exact-boundary records. The same evaluator using the authority boundaries passes 611/611.
- For each of 2,406 Jie, the Month Jian, Officer and Group B month context differ inside a window of up to 377 ms (203.5 s in total over 201 years).

So a production engine that computes its own roots cannot satisfy a Golden anchored on T_JPL unless one side gives way. Domain epsilon is forbidden.

## 3. Recommendation

**Option B: ship the reviewed JPL canonical boundary table as versioned runtime authority data. Retain ERFA as the independent verifier, not as the runtime boundary source.**

- **Runtime contract.** `canonicalBoundary(year, term)` returns the integer TT ms from `golden-v4/astronomy/solar-terms-jpl-de440s-clock-v1` (or a compact, hash-pinned derivative), and civil time comes from clock-v1. Exact semantics: `t ≥ T` → new term. No astronomy is computed on the hot path, no epsilon is used, and nothing is fetched.
- **Integrity.**
  - Ship the table's SHA-256 and verify it at module load; fail closed on mismatch.
  - CI recomputes every row with ERFA and asserts |T_ERFA − T_JPL| ≤ 0.5 s. This catches corruption or encoding errors without letting ERFA define T.
  - CI also re-runs the frozen golden-v4 tests against production.
- **Why not A?** The Golden would be wrong in the 4,808 crossings where ERFA's millisecond differs, or the Golden would have to be regenerated from the engine, which is forbidden. Calling ERFA's millisecond "canonical" would claim accuracy it does not have.
- **Why not C?** It gives the same result as B with about 2.8× the bytes and real compute, and the corrections are themselves a JPL-derived table. C is only worth considering if future range extension needs ERFA anyway.
- **Why not D1 or D2?** D1 makes the less accurate model the authority and requires an engine-generated Golden. D2 reintroduces a tolerance band through fixture placement.
- **What ERFA keeps:**
  1. CI accuracy verification of the shipped table.
  2. An independent source if the supported range is ever extended, which would need a new authority generation from JPL, not ERFA output.
  3. An emergency fallback only under a new, explicitly versioned authority.

  ERFA does **not** need to be bundled into the app under option B.

**Costs and decisions for the owner:**
- This reverses the 3B.4.3 expectation that ERFA computes boundaries at runtime. The 3B.4.3 work (port review, determinism, CSP and offline gates) becomes verification tooling plus a ready fallback.
- It accepts about 19 KB gzipped of authority data. That is smaller than the ERFA bundle (47 KB gzipped).
- Bazi, Officer and Group A/B must all read the same boundary source.
- The device gate is much less demanding: a table lookup instead of an EPV00 evaluation.

## 4. If option B is rejected

The only coherent alternative is **A with an explicit authority change**. The project would declare ERFA canonical T to be the domain boundary, keep JPL as an accuracy gate only, and build a *new* Golden version anchored on T_ERFA, independently verified to lie within 0.5 s of JPL and reviewed by recomputing ERFA from upstream C, not from the production code. That rewrites this spec's Layer C. It is a legitimate product choice, but it is a different authority (`astronomy-authority-v5`), and golden-v4 would not be the production Golden.

## 5. Gate status

The contradiction is **surfaced and resolved by a recommendation (B)**. Phase 3B.4.4B must not start migration until:

1. The owner ratifies B, or ratifies A together with an authority change.
2. The clock-v1 post-2027 pin is signed off.
3. The physical device gate is scheduled. It is much lighter under B.
